# Hermes capability matrix

This is a source inventory, not a release or parity certification. It compares
the documented built-in Hermes tools and selected runtime behavior with the V4
agent tool registry in the current shared checkout. It does **not** establish
what is deployed, configured, or usable with a real account. Other V4 surfaces,
native agents, and explicitly configured MCP servers may offer related features.

Reference: [Hermes v0.22.5 release, commit `bf0203a794a`](https://github.com/NousResearch/hermes-agent/releases/tag/v0.22.5),
and its pinned [built-in tool reference](https://github.com/NousResearch/hermes-agent/blob/bf0203a794a/website/docs/reference/tools-reference.md).
That reference makes availability conditional on platform, toolsets, credentials,
and configuration. The initial V4 inventory used `61f1e21`; selected rows were
updated from source through `97344b0` on branch `fix/macos-app-verification`.
The shared worktree may contain concurrent changes, and these source observations
do not establish what is built or deployed.

Status meanings (exactly one per row):

- **Implemented**: a model-callable or user-visible V4 feature for this
  capability exists in current source and is available without extra account
  setup beyond the platform noted. It does **not** assert Hermes semantic parity;
  listed differences still apply, and nothing here was run against a real provider.
- **Conditional**: implemented, but registered or usable only under the stated
  condition (setting, credential, platform, provider support).
- **Missing**: no equivalent was found in the current V4 agent registry or UI.
  This is not a claim about arbitrary MCP servers or external providers.
- **Not yet assessed**: evidence is insufficient; no parity claim is made.

Core capabilities (file, command, memory, session, schedule, delegation) are
listed separately from optional, provider-, platform- and credential-dependent
ones; Hermes catalogue breadth (messaging, plugins, backends) is not core.

V4 registry evidence: [`tool_definitions`](../../rust/crates/api/src/v4_agent/mod.rs),
[`file and command tools`](../../rust/crates/api/src/v4_agent/tools.rs),
[`knowledge tools`](../../rust/crates/api/src/v4_agent/knowledge.rs),
[`schedule tool`](../../rust/crates/api/src/v4_agent/scheduling.rs),
[`integration registration`](../../rust/crates/api/src/v4_agent/integrations.rs), and
[`browser tools`](../../rust/crates/api/src/v4_agent/browser.rs). The registry
filters out integrations and writes for the internal read-only child policy.

## Core tool mapping

| Hermes capability | V4 status | Evidence and difference to resolve |
| --- | --- | --- |
| `read_file` | Implemented | `read_file` reads workspace UTF-8 files with bounded line pages and byte pages (up to 512 KB per read); symlinks and credential paths are refused. Hermes documents additional document formats. |
| `write_file` | Implemented | `write_file` writes within the workspace with bounded atomic replacement. Hermes's whole-file read baseline and syntax checks were not compared. |
| `patch` | Implemented | `replace_text` replaces one literal match, or an explicit `expected_count`. `apply_patch` applies 1 to 50 hunks atomically (all-or-nothing, one atomic write), with per-hunk `expected_count`, a whitespace-tolerant line match used only when unambiguous, an optional content-hash `expected_revision` rechecked just before writing, and `dry_run`; it is filtered out for read-only children. It takes structured hunks only (no unified-diff format). Optional `validate_syntax` (`json`, `toml` or `yaml`) checks the complete result before writing, in `apply_patch` and dry runs, and refuses an invalid result without writing or executing anything. JSON uses `serde_json`. No TOML, YAML or Python parser crate is in `Cargo.lock`, so TOML and YAML use hand-written structural checkers (`file_patch_syntax.rs`) that reject only definite errors (unterminated strings or brackets, bad escapes, malformed numbers, duplicate keys or tables, tabs used as YAML indentation); they are not full parsers, so a document with a subtler error (an impossible TOML calendar date such as 30 February, or inconsistent YAML sibling indentation) can pass. Python is not supported and is rejected: a correct grammar cannot be hand-rolled safely, and the only available parser would be a host `python3` process, whose version and sandboxing V4 does not control. |
| `search_files` | Implemented | `search_text` (content or filename mode; literal and, on Unix, regex) and `list_files` (one directory). Regex case folding is ASCII-only, long lines may be skipped, scan limits apply, and non-Unix search is unavailable. See the [runtime guide](../features/V4_RUNTIME.md). |
| `terminal` foreground | Implemented | `run_command` needs exact-action approval, runs in the workspace, 60 s limit; unattended tasks deny it. Approved commands have normal host access, not an OS sandbox. |
| `terminal` background/notification modes and `process_manage` (list, poll, read logs, wait, kill, write) | Conditional | `background_start`/`list`/`status`/`wait`/`wait_output`/`follow_output`/`cancel`/`read_output`/`write`/`write_bytes`/`close_input` are registered in the production turn on Unix only when the server starts with `TERMINAL_V4_BACKGROUND_COMMANDS=1` (default off), are never offered to read-only delegated children, and run through the approval-, owner-, session-incarnation- and checkpoint-fenced per-turn actor; completion is delivered to the owning session once as a metadata-only notice. List combines bounded indexed receipts and in-memory entries; older unindexed and pruned actions can be absent. Output activity can be waited for; `background_follow_output` waits and requests private review of the latest bounded output window, with overlap and in-memory retention limits. Interactive starts, UTF-8 or binary writes and input closure require exact approval; operations are bounded and replay-protected and report local pipe state rather than consumption. Binary approval shows the decoded bytes in hexadecimal. Unreviewed streaming log tail remains missing. Verified with scripted-provider turns and real subprocesses; live-provider behavior is unverified. See [BACKGROUND_PROCESS_LIFECYCLE.md](BACKGROUND_PROCESS_LIFECYCLE.md). |
| `execute_code` (programmatic tool orchestration) | Conditional (Unix, needs `python3`) | `execute_code` runs a model-supplied Python 3 script after an exact-action approval that shows the script text verbatim. The script can call `read_file`, `list_files` and `search_text` (plus the write tools when the parent policy allows writes) over a private Unix socket through the same dispatcher and policy as direct calls: at most 50 nested calls, 60 s timeout, 50,000 bytes each for stdout and stderr, scrubbed environment, process group killed on cancel or timeout, result returned as untrusted text. Unattended runs and read-only children cannot use it. On macOS with a working `/usr/bin/sandbox-exec` the script runs under a sandbox profile: the OS denies all network access except the tool socket and denies file writes outside the workspace and temporary directories (tested, including bypassing the Python guard); file reads are NOT restricted. Where `sandbox-exec` is absent or unusable (Linux, nested sandbox) there is no OS boundary: only the best-effort Python network guard applies, and the tool description and approval text say so. Nested calls are not recorded as separate tool events. |
| `delegate_task` | Implemented (Unix) | Approved read-only child in a separate context while the parent waits; `delegate_tasks` runs two to four concurrently. Children get only read/search/recall/skill-read tools. Not available on non-Unix. |
| `delegate_task` background | Conditional | `delegate_task_background` is registered only on Unix, for the Standard tool policy, when the delegation supervisor is present and the provider supports durable tasks. Locally authorized and attested paired-origin results can wake an idle parent, subject to live credential checks and existing queue holds. Synthetic-provider tests exercise delivery, logout and review; two loopback APIs cover paired proxy delivery, graceful restart and explicit recovery after killing an active child supervisor. Real-provider and physical-device behavior are unverified. |
| `clarify` | Implemented | Hermes asks 1-5 questions (single-select, multi-select or open-ended); V4 `ask_user` accepts one to five questions with two to six options, optional `multiSelect`, and one custom answer, bound to the active owner/session/turn. Authenticated route and isolated browser-to-synthetic-provider tests cover multi-select and exact answer delivery. CLI and unattended runs cannot answer. Real-provider behavior remains unverified. |
| `todo_list` | Implemented | Owner/workspace/session-scoped revisioned list with nesting, replace/merge/read and compaction preservation; stricter bounds than Hermes; cleared in rewind forks. |
| `mcp__<server>__*` | Conditional | `mcp_list_servers` is always registered; `mcp_list_tools`, `mcp_call_tool`, resource and prompt wrappers are registered only when at least one MCP server is enabled, and every call needs approval (unattended calls are disabled). |
| `manage_connections` | Missing | Hermes displays, checks, connects, reconnects and renames managed connectors or local MCP servers (needs the Nous Portal to enable connectors; it cannot disconnect or revoke). MCP servers are configured in the UI (`McpSettingsPanel`); no agent-callable management or Hermes managed-connector flow. |
| `manage_catalog` | Missing | Hermes (desktop app sessions only; not in `all`) searches and, with approval, installs catalog plugins and hub skills into the profile. V4 has no agent-callable plugin/skill catalog installation. |

## Browser tools and action safety

All V4 browser and `web_extract` tools are **Conditional** on the account's agent browser setting being enabled (`browser::load_config(...).enabled`); each action needs exact-action approval, is limited to configured origins, and is bound to the reviewed tab and document. V4's own browser is a disposable Chromium profile; when the shared in-app browser is available, `browser_open`, `browser_tabs` and `browser_close` act on the human-visible browser instead.

| Hermes capability | V4 status | Evidence and difference to resolve |
| --- | --- | --- |
| `browser_navigate`, `browser_back`, `browser_snapshot`, `browser_click`, `browser_type`, `browser_scroll` | Conditional | Registered with the agent browser. Refs come from the latest snapshot; stale refs are rejected; password values are redacted. Snapshot semantics differ from Hermes. V4 additionally registers `browser_open`, `browser_forward`, `browser_select`, `browser_wait`, `browser_tabs`, `browser_close`. |
| `browser_vision` | Conditional | Hermes screenshots the page and falls back to an auxiliary vision model on text-only models. `browser_screenshot` returns the active tab viewport as a PNG. Hermes also describes a fallback vision route; whether the selected V4 model accepts tool images must be checked per model. |
| `browser_get_images` | Conditional | Registered with the agent browser. Lists bounded image URLs and alt text from the reviewed document and open shadow roots; does not fetch images, read closed shadow roots or iframes. URLs may be sensitive. |
| `browser_press` | Missing | A prototype exists only in test paths and is not registered. Both isolated and shared prototypes retain the settings lease while a key release is pending or unconfirmed; the shared modal path has a synthetic browser UI test. A Chromium test shows a focus handler can redirect a key away from the reviewed ref, so the approved target is not enforceable. `browser_evaluate` (approved script) does not establish native key behavior. |

| `browser_exec` | Missing | The tools reference names it (with five vault tools) only in its intro count and lists no description. Not a rendering or provider extractor. |

## Providers and execution environments

| Capability | V4 status | Evidence and work to establish parity |
| --- | --- | --- |
| Provider routes | Conditional | The agent loop (`supports`) runs a catalogued provider only if auth is `api-key` and transport is `openai-chat`, `openai-responses` or `anthropic-messages`: 37 of 40 entries in [`agent_provider_definitions.json`](../../rust/crates/api/src/agent_provider_definitions.json) (including OpenRouter, xAI, DeepSeek, Nous, LM Studio, Fireworks, Ollama Cloud and the three cloud routes below). Each needs its own credential or local server. Not in the agent loop: `copilot`, `moa`, `copilot-acp` (see below). Hermes keeps its providers under `plugins/model-providers/` (per-provider enumeration **not yet assessed**); do not claim parity from the count. |
| Cloud routes: Azure AI Foundry / Azure OpenAI, AWS Bedrock, Google Vertex AI | Implemented, mock-verified only | Catalogued api-key providers (`cloud` field in the definitions) in [`cloud_provider.rs`](../../rust/crates/api/src/v4_agent/cloud_provider.rs). Settings are validated, stored encrypted together with the key in the existing vault slot (`PUT /api/agent/auth/{provider}/api-key` with `settings`; the Provider authentication modal renders the required fields), and never returned. **Azure**: HTTPS endpoint restricted to `*.openai.azure.com`, `*.services.ai.azure.com`, `*.cognitiveservices.azure.com` (and `.us`/`.cn` variants), no port, path, query, credentials or IP literals; `apiVersion` required; `api-key` header (default) or bearer; chat uses `/openai/deployments/{model}/chat/completions?api-version=`, Responses models use `/openai/responses?api-version=`, `apiVersion: v1` uses `/openai/v1/...`. The V4 model name is the Azure deployment name (no separate deployment override). **Bedrock**: two credential forms in the same vault slot. (1) A Bedrock API key as bearer against `https://bedrock-runtime.{region}.amazonaws.com/openai/v1/chat/completions` (OpenAI-compatible Chat Completions; gpt-oss models). (2) Minified JSON `{"accessKeyId","secretAccessKey","sessionToken"?}`: requests are signed with SigV4 (service `bedrock`, own implementation over `sha2`, no new dependency; session token signed as `x-amz-security-token`) and sent to the non-streaming Converse API `POST /model/{modelId}/converse` (model ID percent-encoded once in the URL, canonical URI double-encoded; ID charset restricted so it cannot alter the path). OpenAI-shaped history, tools (`toolSpec`/`toolUse`/`toolResult`), `data:` images (png/jpeg/gif/webp) and `max_tokens` are translated and the reply is mapped back to a chat completion, so the agent loop is unchanged. The reply arrives as one text delta, not incrementally: ConverseStream (binary event-stream framing) is **not implemented**. Not supported: IAM role/profile/ADC resolution from the environment, credential refresh, guardrails, prompt caching, document blocks, reasoning-effort mapping. **Vertex**: OpenAI-compatible `.../v1/projects/{project}/locations/{location}/endpoints/openapi/chat/completions`. Credential is either a pasted OAuth access token (expires after about an hour) or a minified service-account JSON key: an RS256 JWT (`iss`=client email, `scope`=cloud-platform, `aud`=token endpoint, `iat`, `exp`=iat+3600, `kid` from `private_key_id`) is exchanged at the token endpoint (jwt-bearer grant) for an access token cached in memory per (account, endpoint, key hash) until `expires_in` minus 60 s; the key, assertion and token are never logged, stored in sessions or returned, and token-exchange errors carry only the HTTP status. The production token endpoint is pinned to `https://oauth2.googleapis.com/token` (the key file's `token_uri` is ignored); a `tokenEndpoint` setting is accepted only on loopback when `TERMINAL_V4_CLOUD_PROVIDER_ALLOW_LOOPBACK=1` (tests). Not supported: ADC from the environment/metadata server, user (`authorized_user`) credentials, impersonation, workload identity federation. Key save (`agent_catalog.rs`) accepts a pretty-printed multi-line JSON key only for the Vertex (service-account fields) and Bedrock (`accessKeyId` and `secretAccessKey`) providers, when it parses as the expected JSON object; it is normalised to minified JSON before storage and the value is never logged or echoed. Every other provider keeps the strict no-control-characters check, and malformed or wrongly shaped JSON gets a generic rejection. The Provider authentication modal shows a masked multi-line textarea for the Vertex and Bedrock key (a single-line password input for every other provider) so JSON can be pasted as is; component tests only, not run against the server; no dedicated JSON upload UI. Same request budget (24 MB body, 8 MB stream), 120 s timeout, no redirects, per-turn cancellation as other providers; HTTP errors map to fixed hints and never include the response body or URL. Loopback endpoints are accepted only when `TERMINAL_V4_CLOUD_PROVIDER_ALLOW_LOOPBACK=1` (tests). Verified only against local mock servers (exact URL, headers, payload, streamed tool-call round trip, error mapping, cancellation, settings validation; SigV4 against AWS's published signing-key and test-suite vectors plus an independent HMAC/date check; Converse request/response translation and a signed tool-call round trip; JWT shape verified with the public key, mock token exchange, expiry-driven re-mint, secret non-leakage); **needs real-account verification** (SigV4/Converse acceptance by a real Bedrock endpoint and model availability, Google acceptance of the minted assertion and scopes, Vertex model availability, API-version acceptance, `max_tokens` handling on newer Azure reasoning models, token expiry behavior). |
| `copilot` | Not supported (investigated, not feasible with public documentation) | Copilot model inference at `api.githubcopilot.com` is not a documented public API: it needs a short-lived Copilot session token exchanged from a GitHub token via an internal endpoint (`api.github.com/copilot_internal/...`) that GitHub does not document or support for third-party clients, plus editor-identity headers, and the OAuth client IDs that work belong to GitHub's own first-party integrations. There is no documented static API key. Building it would depend on undocumented behavior and could breach GitHub's terms, and it could not be verified against a mock that reflects the real contract, so nothing is implemented; the catalog entry stays `auth: oauth` and unsupported in the agent loop. Revisit only if GitHub publishes a supported inference API for third-party clients. |
| `moa`, `copilot-acp` | Not model providers | `moa` is a virtual ensemble and `copilot-acp` an external CLI speaking ACP (stdio) rather than an HTTP model protocol; neither fits the openai-chat/responses/anthropic-messages loop, and Hermes's `moa` also fans out to other configured providers. Not implemented. |
| Streaming, tool-loop limits, cancellation | Implemented | Streams supported formats, bounds requests, scoped interaction/cancellation. Retry, incomplete-turn and reconnect behavior per provider not compared. |
| Execution environments | Local (implemented); Docker (conditional, fake daemon only); SSH (conditional, loopback-verified) | V4 selects local, Docker or SSH with `V4_RUN_COMMAND_BACKEND`. **Docker**: read-write workspace mount, resource limits, disabled networking by default, a unique named container with a cidfile and ownership labels, and verified removal after completion, timeout, cancellation and a dropped run future (kill, `rm -f` by name and by cidfile id, then a listing check; a failed removal stays owned, blocks later commands and is retried). A container the daemon creates after the client was killed is polled for up to 2.5 s and removed. Only a cidfile that is a plain container id is ever passed to Docker. At server start a reaper removes labelled containers whose recorded server process is dead (a failed removal is not counted and is retried next start; a reused PID of an unrelated live process hides a leaked container). All of this is tested against a fake Docker executable, **not a real daemon**; real-daemon behavior (create latency beyond 2.5 s, cidfile timing, label filters) is unverified. **SSH**: the remote command runs through a wrapper that requires its shell to be a process-group leader (otherwise it refuses to run), records the group in a mode-0600 pidfile under `/tmp`, starts a 120 s remote watchdog that kills the group, then execs the command. Completion, timeout, cancellation and drop run a second SSH connection that first writes a stop marker (so a late-starting wrapper refuses), then TERMs, KILLs and probes the group until it is gone, accepting only a numeric pidfile greater than 1; the result is reported as confirmed only when the probe prints its `gone` or `absent` line, otherwise `Remote command cleanup is unconfirmed`, which stays owned, blocks later commands and is retried on close. Tested with a fake `ssh` that runs the remote command detached from the client (new session, not a descendant), where the remote survives a killed client until the probe runs and is then dead with no leftover files, and with a gated real loopback `sshd` test (`V4_TEST_LOOPBACK_SSHD=1`, macOS, run once on a non-3030 port): a timed-out command and its background child were killed and left no pidfile. Remaining gaps: a descendant that starts its own session or process group escapes the group kill (the 120 s watchdog does not catch it either); an unreachable host, including a refused host key, reports cleanup unconfirmed instead of the ssh exit status and blocks the next command until retried; if V4 itself dies the watchdog (120 s) is the only remote protection and there is no restart reaper for stale `/tmp/.v4-run-*` pidfiles or stop markers; the remote needs a POSIX login shell, `/bin/sh`, `ps`, `tr`, `kill`, `sleep` and a writable `/tmp`; not tested against a Linux sshd or dash. Hermes also lists `modal`, `managed_modal`, `daytona` and `vercel_sandbox`; V4 has no established equivalents for those environments. Paired-environment remoting targets another V4 host and is a separate feature. |

## Prerequisites for an indexed recall implementation

A complete index must cover V4, structured, PTY and imported histories. An
index filled only by queries can omit new or changed conversations, so it must
not claim complete search results. A design should establish:

- Owner- and workspace-bound identities, verified on reads, with only redacted
  searchable text; terminal fragments must be reassembled before redaction.
- A durable source-change record or equivalent recovery protocol for every
  create, update and deletion, including crashes between source and index
  writes. Deleted records require durable tombstones until index cleanup is
  confirmed. Existing history sources do not share one transaction.
- Bounded, restartable shadow-generation rebuilds with source watermarks,
  per-record and total storage limits, and explicit handling of corruption,
  symlinks, oversized records and interrupted rebuilds. Incomplete freshness
  must be reported or use the existing bounded scan rather than implying a
  complete negative result.
- Pagination bound to the owner, workspace, query, filters and immutable index
  generation; changed or expired generations must reject continuation. Source
  revisions must be checked when returning hits.
- Integration tests across all sources for ownership, redaction, mutation,
  deletion, rebuild, crash boundaries, concurrent writers, limits and stale
  pagination, before claiming global relevance or FTS parity.

### Indexed recall status

Implemented behind a default-OFF setting; enable only after validating on real data:

- Identity: one SQLite database per hashed owner under `<data>/recall-index/`; owner is verified in metadata and every row, workspace filters use the normalized workspace key, symlinked storage is refused, copied or corrupt databases are quarantined.
- Text: only `safe_history_text`-redacted text is stored; terminal fragments are reassembled before redaction and private keys spanning messages are withheld.
- Change record: every create, update and delete is written to a durable journal before it is applied; deletes keep a tombstone until the index confirms no rows remain. Source files have no shared transaction, so changes are also detected by diffing the source manifest (size and mtime) on each search.
- Rebuild: shadow generation with a persisted queue and watermark, resumable after a kill, catch-up passes before an atomic activation, per-record (2 MB), total (256 MB) and manifest (50,000) limits, oversized or unreadable records counted as skipped.
- Pagination: `indexCursor` binds owner, workspace, query, filters and generation revision; any change or rebuild rejects continuation. Hit file revisions are re-checked before results are returned.
- Freshness: if the index is rebuilding, over a limit, has pending changes beyond the per-search budget, or a source changed mid-search, the bounded scan answers and `index.used=false` with a reason.
- Not claimed: scan substring parity, global relevance, or Hermes FTS parity. Queries with no alphanumeric term use the scan.
