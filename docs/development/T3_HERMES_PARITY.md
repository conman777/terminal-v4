# T3 and Hermes feature parity

This is a working inventory, not a claim of complete parity or live deployment.
Compare V4's observable behavior, permissions and recovery against the reference
feature, then verify it in the integrated application before marking it done.
Source-only observations can become stale in the shared checkout.
Detailed scoped mappings live in the [T3 capability matrix](T3_CAPABILITY_MATRIX.md)
and [Hermes capability matrix](HERMES_CAPABILITY_MATRIX.md).

Reference points:

- T3 web source: commit [`5f64c5eb299a23d278ef043c416bd4dc801bc53c`](https://github.com/pingdotgg/t3code/tree/5f64c5eb299a23d278ef043c416bd4dc801bc53c).
- Hermes project baseline: commit [`79651b71bd56efd76d06f3de1df64dde09b58ff3`](https://github.com/NousResearch/hermes-agent/tree/79651b71bd56efd76d06f3de1df64dde09b58ff3).
- Newer Hermes reference: [v0.22.5](https://github.com/NousResearch/hermes-agent/releases/tag/v0.22.5), including its [tool reference](https://github.com/NousResearch/hermes-agent/blob/bf0203a794a/website/docs/reference/tools-reference.md).

The available T3 phone-screen reference is native source; it does not establish
the behavior of T3's mobile browser. Expand this inventory across the reference
releases, configurations and integrations before declaring full coverage.

## UI and conversation

| Area | Current evidence | Remaining work |
| --- | --- | --- |
| Desktop and mobile navigation | Thread navigation, saved-message search and mobile sign-out are implemented in source. Phone-width fixture checks cover sign-out and same-account text draft recovery. | Verify integrated workflows and exact-match behavior. Terminal output and legacy messages without IDs cannot jump to an exact position. |
| Mobile thread terminal | Desktop and mobile source provide a thread-owned terminal drawer. Isolated real-backend Chromium checks at 320 and 390 pixels cover PTY input, thread switching, reload, restarting an ended shell in the same terminal, and draft preservation. Scoped retries preserve other terminals after out-of-order failures, and an add failure does not hide a working terminal. | Terminal create, restore and link requests now revalidate credentials after each lock wait and roll back a terminal created for a revoked owner; create accepts an owner-scoped idempotent request id and links the terminal to its thread atomically. A revocation after the final check can still leave a created terminal, and restore has no check after the shell is published. The retry handle for a created-but-unlinked terminal is kept in the tab's sessionStorage: it survives reload and unmount but not closing the tab, and another tab cannot see it. Only the first terminal of an empty thread is deduplicated across tabs; an unconfirmed create still needs manual review before starting again. Browser emulation does not establish physical phone keyboard behavior. |
| Mobile composer | Compact composer, dictation, file mentions, skills and supported Claude/Codex model controls exist in source. The new-thread input and send button were checked at 320 and 390 pixels. | Verify microphone and attachment behavior against real providers; compare remaining model and mode controls with desktop and the reference. |
| Conversation actions | Desktop and mobile have edit, fork and plan actions for supported Codex and Claude sessions, with draft preservation checks. | Verify real-provider behavior and remaining runtimes. |
| Thread lifecycle | Structured conversations can be snoozed for an hour and manually woken. Idle V4 conversations can be manually settled on supported Unix servers; a visible shelf preserves drafts and the server checks pending queue work, requests and unresolved delegated children. New user or queue activity wakes them, while a restart hold alone does not. Working threads remain visible while offscreen approval state is polled; renewed touch or other activity after idle requests a refresh. | Verify full integrated lifecycle and separately tracked requests; an approval indicator may lag until the next successful inventory refresh. Automatic settlement, pull-request rules, terminal cleanup and settlement for native Claude/Codex or terminal sessions remain unfinished. The existing terminal activity heuristic is not sufficient for hiding threads. |
| Context and new threads | V4 supports slash commands, file mentions, bounded project-content search and worktrees with a chosen base ref. | Compare inline context workflows, attachment support and branch discovery with T3. Project-content search is Unix-only and does not jump to an editor line. |
| Queue and approvals | Pending decisions appear near the composer. Unix local and paired queue reads and mutations revalidate credentials after waiting; uncertain published mutations retain their operation identity. The panel preserves a recovered-receipt reminder and offers an explicit Wake action. A non-default preview binds V4 queued turns to signed local authority and session incarnation; default Wake holds pending work for review. | Server-owned native Claude/Codex queue dispatch is not integrated; groundwork exists (a non-blocking per-session lease on Codex and native Claude sends, and a durable request-id ledger so a native Claude send returns a real receipt that can be reconciled as accepted or absent after a crash, see [session ownership](STRUCTURED_SESSION_OWNERSHIP.md)). Still blocking: native scope for queue holds, an idle boundary to trigger drain, signed-authority binding of native queue items, the Codex approval and workspace-activity fences, and the lease covering input, callbacks, approvals and delete. V4 preview needs integrated and paired-credential coverage before release; unproven legacy and paired items lack durable dispatch proofs, and the existing default Resume path retains legacy authorization behavior. Legacy preview proofs are held for local reauthorization. Preview key installation now has unit, route and real-binary coverage for cancellation, crash ordering and unconfirmed commits. One owner's damaged queue is preserved and held for that owner only. Installation is still blocked for everyone while a readable queue names an installation but the marker is missing, or when damage cannot be attributed to an owner. The initial scan holds authorization and queue locks with a 10-second budget; a single blocking filesystem call can still exceed it. Preserve the dedicated key and installation marker together; a lost key is never recreated over an existing marker, and restoring it recovers held work. The marker is bound to the canonical data-directory path, so moving the directory invalidates protected work until reviewed. Mixed old and new server versions sharing a data directory are unsupported. A recovered receipt alone does not guarantee dispatch. Non-Unix read fencing is weaker, and filesystem I/O while authorization fences are held can delay logout or paired revocation. Verify cross-device drafts. |
| Attachment drafts | Source changes retain selected file paths across thread and pane switches and recover path metadata after reload, scoped to the account, environment and thread. When another tab changes the saved selection, the composer keeps the current files and message, blocks sending, and lets the user compare paths and explicitly adopt the saved selection without overwriting it. It checks for a missed storage event immediately before sending and rejects an upload begun before the selection was replaced. Isolated two-tab Chromium checks cover review and a stale review at phone and desktop widths. | Verify the integrated app and real providers; restored paths may have changed or disappeared. LocalStorage comparison and writing are not atomic across tabs, so simultaneous writes or a change after the pre-send check can still race. One intermittent mobile browser assertion remains unexplained. |

## Agent runtime

| Area | Current evidence | Remaining work |
| --- | --- | --- |
| Delegation | Unix V4 source exposes approved read-only foreground single and parallel investigations, and can expose background delegation when its supervisor is available. See [runtime delegation](../features/V4_RUNTIME.md). | Real-path synthetic-provider tests cover reviewed approval, enforced read-only child tools, exactly-once delivery, parent cancel, logout, restart and deleted-parent handling. Since then: a full ledger now prunes the oldest delivered records and keeps a tombstone per pruned record, so replays of pruned requests are still refused (undelivered, uncertain and unfinished records are never pruned); each read-only child holds a lifeline pipe from its supervisor and kills its own process group when the supervisor dies (a SIGSTOPped supervisor is not detected; tested with a real process tree); finished-but-undelivered results, including a deleted parent's, are returned in the cleanup review payload as `results` (the cleanup review UI does not display them yet); and the wake-parent end-to-end spec passed at 320, 393 and 1440 pixels against both the default and `queued-authority-preview` builds with a synthetic provider. Still open: live-provider verification, UI for the retained results, and recovery of unfinished children still needs the owner's review. The default build holds results for review instead of waking the parent. Compare writable delegation later. |
| Background commands | The tool interface remains test-only. Unix source reopens an existing manager and integrates session deletion, shutdown and reviewed recovery. Cross-process tests cover first provisioning against deletion, owner/session lock contention, crash release and manager reacquisition. | Status, wait, cancel and reviewed output now run only through the incarnation- and checkpoint-fenced actor, with per-owner, per-session and global capacity limits; tests cover restart and logout boundaries. Since then: an authorized standalone review can clear a crash-left unknown claim without replaying it (backend only: no HTTP route or UI yet); finished receipts are pruned oldest-first when a scope is full (running, unknown and reviewed-unknown claims and each session's newest 8 are kept); a metadata-only completion event is published after the ledger commit (nothing consumes it yet); and a running command, an unreviewed unknown outcome or unconfirmed cleanup now blocks thread settlement and the lifecycle projection. Before enabling: add the review route and panel, call `open_or_provision` at trusted startup, consume completion events, bound the launch boundary that holds a SQLite write transaction during spawn (and test Stop under a stalled launch), and decide the recovery policy for escaped processes. Output is still in memory only. The tools stay disabled in production. |
| Logout and admission | Unix source orders local V4 message publication against logout and includes a structured-session, delegation and background cleanup coordinator. Thread metadata and title PATCH routes, and Stop, have scoped post-wait authorization checks in source. An uncertain title update is reviewed after a no-cache refresh before another same-tab write. | Verify integrated startup, recovery and cross-process cleanup. Structured list, get and inventory reads revalidate local and paired credentials after every wait, before each recovery checkpoint and before publishing, and omit sessions deleted mid-read; recovery is not atomic across checkpoints and a session whose delete is still in flight is not hidden. Browser and MCP resources still use process-local logout cleanup. The fence assumes a private, stable data directory; the equivalent Windows boundary remains unverified. |
| Agent questions | The V4 structured runtime can request an owner-bound answer with choices or free text. | Compare Hermes question batching and presentation; unattended and CLI runs cannot answer. |
| Scheduling | One-shot, interval, named-zone and reviewed agent creation exist in source. Shutdown interrupts a task waiting for the checkpoint lock; an already-started checkpoint is awaited. | A durable `worker-protocol.json` marker, written only under the exclusive worker lease, makes an older worker refuse to start against newer data; oversized outcomes now fall back to a compact receipt instead of being lost (see [worker upgrade](WORKER_UPGRADE.md)). Still open: if the owner-store write and every receipt write keep failing, process exit leaves the task `interrupted` with its result lost; after downtime, missed runs coalesce into one catch-up run with no skip window; an active checkpoint can delay shutdown up to the existing 10-second wait; and management, timing and delivery parity with the newer reference is not audited. Old and new workers must not share a data directory concurrently. |
| Memory, skills and recall | Reviewed memory, optional on-demand skills, bounded recall and compaction exist. | Compare learning, snapshot timing, search quality and compaction options; retain owner isolation and reviewed writes. |
| Browser, web and media | Approved browser/MCP operations and image inputs exist. | Inventory search, generation, audio, video and computer-use workflows and their credentials and platform requirements. |
| Messaging | Telegram gateway code exists locally. | Verify it independently and inventory other Hermes channels and delivery capabilities. |
| Providers and environments | V4 supports several provider protocols and local execution. | Inventory additional provider transports and execution environments, then test configured integrations separately from mocked protocols. |

## Release evidence

- Verify the current source on a stable snapshot with the full frontend and Rust
  suites and isolated integration tests.
- Test desktop and mobile browser workflows, including draft retention,
  microphone lifecycle, approvals, terminal access and reconnects. A real iPhone
  check is a follow-up, not the initial release gate.
- Keep unverified or unsafe features disabled; distinguish source changes from
  what is actually served on Tailscale.
- Complete queued authorization and its logout, session cleanup and recovery
  boundaries before enabling it or the background command tools.
- Upgrade backend and frontend together using a controlled worker transition.
  Never run an older worker and a newer worker concurrently on the same store.
