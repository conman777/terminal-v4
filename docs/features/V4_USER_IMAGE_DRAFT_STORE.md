# User image draft storage

The coherent source candidate uses this native storage module through the stable composer facade and shared desktop/mobile image controller. Source-bound central and native utility gates have passed; compiled-App recovery/provider and installed-release evidence remain separate. The module itself adds no HTTP, global authentication mutation, React controller or object URLs.

## API and authority

`frontend/src/utils/userImageDraftStore.js` exports one scoped adapter factory and a pure head decoder. The frozen base API is retained in the task artifact `work/parity/user-image-idb-api.json`, SHA256 `378500a7777ea6bd5c0ca2d10ae43efe703108614e55288e4954392fa2083407`. It is review documentation, not a runtime dependency. The earlier unavailable scaffold and RED receipts remain immutable evidence.

The trusted scope is `[ownerId, canonicalFullHomeUrlIncludingPath, environmentKey, sessionId]`, with `JSON.stringify(scope)` for the shared facade identity. Normal authenticated home access includes mobile. Paired image operations are denied before DB work; this utility adds no paired grants. Construction validates the scope but opens no database or task. The controller must supply a synchronous live scope check and AbortSignal, and reject stale callbacks before taking any HTTP action.

The adapter preserves displayed raw text/revision separately from committed revision. Promoted `setText` updates the buffer immediately and queues a local save; `flush` awaits required persistence. A later acknowledgment cannot restore older text. `subscribe` removes only that listener; final `close` aborts active storage transactions, closes its DB/channel and fences callbacks without deleting recovery data. React view refcounts, transport abort and object URL lifecycle belong to the shared controller; retiring one view does not close another live view’s store.

## Native storage

Database `v4-composer-images`, version 1, has out-of-line `records` and `blobs` stores:

| Key | Value |
|---|---|
| `records: ['scope', ...scope]` | Validated head, raw draft/revision/ordered local IDs, frozen pending body/pins, removal jobs, retained migration evidence. |
| `records: ['budget', ownerId, fullHomeUrl]` | Account/home byte, Blob-row and scope counters. |
| `blobs: [...scope, localId]` | Actual immutable Blob and its metadata/hash/upload state. |

Each write reads the current head, scoped rows and account/home counters in one native readwrite transaction covering both stores. It compares the expected revision/authority, applies targeted changes and commits the head/Blob/counter changes together. It resolves only after native `complete`. Blob reads/digests and other awaits occur outside active transactions. An aborted transaction never returns a durable success.

Approved admission limits are eight images/16 MiB per message, 8 MiB each; account/full-home cache 64 MiB/256 Blob rows/128 promoted scopes; 4 MiB head metadata and the existing 1,000,000-byte legacy source cap. No automatic eviction removes uncertain/pending data. The account counter is checked against current scoped native rows/counts before writes. Failure retains input and reports a bounded typed error.

Ordinary `rawSha256` is separate from the descriptor's `artifactId`: the latter is SHA256(UTF8 `v4-image-v1`, one NUL byte, UTF8 MIME, one NUL byte, actual image bytes). Local Blob reads and hydration verify hashes. The server remains the image-format/decoding authority. Unsupported/invalid bytes cannot gain readiness from filename alone.

## Draft, upload and send states

`addFiles` validates the entire batch and persists the current raw draft plus ordered immutable Blob rows before returning. It does not upload. A failed transaction retains the attempted File/Blob batch in memory, with no durable/readiness claim; it is not guaranteed to survive reload before a successful commit. An explicit retry may resubmit that same batch, or the user can remove its retained local entry.

`beginUpload` commits an immutable upload UUID/generation and returns the actual verified Blob ticket. The controller performs HTTP. `completeUpload` checks that exact local ticket, generation, typed hash, MIME/name/size and ready receipt, including `attachmentId === ticket.uploadId`. Every persisted descriptor must retain that same row upload UUID, including restored rows. Delayed removed/obsolete results cannot restore a chip. `expiresAt` uses Unix milliseconds. Reloaded in-flight uploads appear unresolved and require explicit retry; hydration does not upload.

`prepareIntent({text, attachments, draftRevision, localIds})` consumes canonical text verbatim. The existing hook is the sole raw-image projector; this module never projects it again. It validates exact ready refs, actual bytes, selection order and revision, then persists one immutable UUID/body/pins before resolving. Matching preparations reuse that UUID/body. A different unresolved intent cannot be replaced. Retry uses `getPendingIntent` and the exact frozen serialized body, with no projection/new ID.

`confirmIntent({requestId, receipt})` requires ordinary request/turn/message/sequence identity and exact image input echo. Confirmation first commits accepted proof while preserving the source draft and all pending pins. This proof-only write must compare the facade's original authority and base draft revision before writing; observing a foreign saved draft does not grant permission to overwrite it. An existing proof fixes request/turn/message/sequence/input identity, while its lifecycle status may advance.

Immediately after that native transaction completes, one synchronous decision compares the complete displayed source revision and ordered local IDs. An unchanged accepted source may be visibly cleared then; a newer raw draft retains its full image selection. Subsequent typing inherits the selection actually displayed at that boundary. A separate native transaction compares the exact proof-stage authority/head revision, full persisted draft and full pending/proof token before atomically persisting the chosen current raw draft, settling pending, releasing only unreferenced pins and updating counters. Image changes remain actor-queued; later raw typing is preserved by revision at completion.

`committed:true` is returned only after the final settlement transaction completes. A proof-stage abort leaves the original native state unchanged. If final settlement fails, the proof-only state may already be durable: `pending.acceptedReceipt`, original body/UUID, source draft and pins remain available, while the chosen local dirty buffer is retained in memory. The caller must distinguish accepted outcome from incomplete local cleanup and must not POST a new body. Read-only hydration exposes this recovery state without finishing it; explicit exact confirmation may retry final cleanup. Dirty raw text that never committed is not claimed to survive a crash.

This proof-only intermediate commit is a root-approved additive clarification of the historical API 378500, whose artifact remains unchanged. Final settlement, revision/selection cleanup, Blob GC and counter changes still commit together. A failure is not a durable final success, and a foreign revision conflict is never silently rebased.

Removing a draft image preserves a pending-send pin and never creates a cancellation job for that pinned target. Unpinned possible publication creates a durable removal job and retains its row/metadata until `completeRemoval`. `getBlob(job.localId)` can recover immutable removal display metadata after reload. The caller must confirm remote cancellation before settling the job; abort is not cancellation proof.

### Approved additive result clarification

`removeImage` normally returns the committed native result. Removing **only** an unsaved in-memory failed Add entry returns `{committed:false, reason:'local_only', snapshot}`. That branch performs no DB/budget/pin/HTTP mutation and retains scope/close guards. It must not claim durable success for a transaction that never existed. Root approved this addition after the frozen base API; the historical API file remains unchanged.

A missing persisted draft row remains a visible `durability:'missing'` placeholder, never a fabricated ready descriptor. If its filename/MIME/size cannot be recovered, display metadata is `Unavailable image`, empty MIME and zero byte count, with `uploadId:null` and `errorCode:'missing_bytes'`. These values are presentation placeholders, not admissible upload/send authority. Readable raw/identity metadata remains visible when binary/counter validation fails, and storage authority stays unavailable.

## Legacy promotion and concurrent writers

Unpromoted text stays on its existing synchronous store. An explicit image action copies the exact version 1 source/raw text/revision/pending UUID to IDB, validates committed readback, checks the legacy source, writes/checks the cooperation marker and finally commits `ready`. The final transaction rereads authority, migration state, head/draft revision and retained source identity before synchronous marker work and the ready transition. A concurrent ready head is a validated observation, not permission to rewrite it; dirty input cannot gain a new overwrite base from that observation. A current conflict is never reset to ready. A marker failure leaves `copy_committed`, and read-only hydration never finishes that promotion automatically. The source snapshot is retained after marker publication. A marker without its IDB head cannot seed a new identity.

Legacy image metadata may have no Blob. Import the exact prior UUID/canonical text/ordered manifest plus missing-byte pins and show that loss. Receipt-only resolution remains possible without bytes. A 404 is not authority to drop images, change body or create a new UUID. `restorePendingBytes` consumes one File/Blob for each current missing-byte pin, in that pin array's order. It admits only the exact original MIME/bytes/name/typed hash and preserves each original local ID and attachment/upload UUID, as well as the frozen body. Duplicate matching occurrences remain separate pins; the caller may repeat the same matching Blob in their array positions. This local restoration does not upload or send. An unproven imported raw draft is not cleared on settlement.

The joined controller separates native read-only hydration from writable recovery admission. After reading an imported image pending with missing pins, a current writable owned/home view may locally prepare its legacy/copy_committed head when existing send/save/upload/restore work is not active. A read-only view cannot authorize promotion. The owning view/native epoch and old preparation promise remain retirement barriers; stale/ABA callbacks cannot restart that writer. Promotion failure keeps the source and blocks original selection rather than silently falling back.

The original-file chooser keeps transient per-pin choices until explicit Save original images. Duplicate occurrences require separate ordered choices; no deduplication or guess from filename is made. Native restore verifies actual typed bytes, commits only exact matching pins and preserves frozen identity/newer draft. Saving performs no HTTP; Check and Retry are separate actions. Model capability does not block local restoration, but it remains required before an image Retry POST after 404.

Same-version writers serialize through native transactions. A stale revision returns conflict, preserving its dirty buffer and the current saved head/pending identity. BroadcastChannel carries only scope digest and revision as an advisory notice; it never imports a remote snapshot or silently rebases dirty text. Actual DB comparisons remain authoritative.

LocalStorage and IDB are not one transaction. Every observed legacy/marker divergence holds actions and retains the sources; explicit mutation may retain bounded conflict evidence in the head. Read-only hydration writes no head/marker. An arbitrary old/uncooperative writer can race a marker check; this slice does not claim universal cross-window migration atomicity or invisible-race loss prevention. There is no destructive automatic repair.

## Obsolete preview reads

`getBlob` still rejects a valid-ID lookup whose row has already been collected. That rejection is quiet only when both current and saved heads have identical authority/head revision, the adapter is ready, and neither head retains the target through its draft, pending pins or removal jobs. The caller receives the rejection, but the adapter does not replace a prior error or publish another public snapshot for this obsolete lookup. This avoids a stale preview error turning a healthy composer into an alert loop after cleanup.

A retained missing row, different saved authority/revision, corrupt bytes or other real failure keeps normal error/conflict reporting. The policy neither clears existing errors nor suppresses all missing-byte failures. It performs no DB mutation and provides no readiness or upload authority.
