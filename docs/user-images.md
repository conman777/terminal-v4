# User images in owned V4 conversations

This document describes the owned backend user-image API and its coherent frontend source candidate. General files, audio/video, document extraction, media conversion and paired-host attachments remain future work. Source/fixture verification is separate from compiled-App recovery/provider and installed-release evidence.

## Owner API

Normal account authentication applies, including an authenticated mobile client using its configured home server. Paired device capabilities cannot upload, read, cancel or send through the attachment prefix. Paths and external URLs never authorize server filesystem reads or downloads.

| Action | Route |
|---|---|
| Upload actual bytes | `POST /api/structured/sessions/{id}/attachments` multipart `uploadId` UUID plus exactly one `image` |
| Inspect uploaded descriptor | `GET .../attachments/{attachmentId}` |
| Read uploaded image | `GET .../attachments/{attachmentId}/content` with normal account auth |
| Release staging | `DELETE .../attachments/{attachmentId}` |
| Send an immutable image intent | `POST .../attachments/send` JSON `{requestId,text,attachments}` |
| Recover accepted identity | `GET /api/structured/sessions/{id}/requests/{requestId}` |

A descriptor is exactly `{attachmentId,artifactId,mimeType,bytes,name}`. Attachment IDs are canonical lowercase UUIDs; artifact IDs are 64 lowercase hexadecimal characters from a typed SHA256 over full MIME and bytes. Names are 1–255 UTF8 bytes without control characters, slash or backslash. Names are display metadata. The server derives owner, normalized canonical workspace and engine UUID from the authoritative session.

First successful upload returns 201; a duplicate committed identical upload identity returns 200. Ready responses include `status`, `attachment` and integer epoch-millisecond `expiresAt`. Image content uses its validated MIME with `private, no-store` and `nosniff` headers. Cancelled or expired unaccepted content returns 410. Deleted/foreign sessions return 404. Reusing an upload identity for different bytes or metadata returns 409.

Only PNG, JPEG, GIF and WebP are accepted; the user-image slice rejects unsupported animation rather than selecting a frame. Validation checks bounded container signatures/framing/dimensions, not full pixel decoding. The maximum is 8 MiB per file and 8 ordered references/16MiB decoded per send. Upload/tombstone identity storage is bounded at 1,024 identities per conversation; immutable image storage is bounded at 256 files/64MiB per engine scope. Staging uses its own bounded private quota, including registry metadata. Repeated references remain ordered and count again for inference limits. Existing history and new images together must fit 32 images/16MiB hydration and the final 24,000,000-byte serialized provider request before a new accepted event. These checks do not resolve a key, invoke MCP, call a provider or trigger inference/automatic compaction.

## Acceptance and recovery

Image-only sends use `text:""`. The new route maps CRLF to LF, trims the shared Rust whitespace set (including NEL, excluding BOM), preserves decomposed Unicode and never normalizes NFC. Clients keep raw draft bytes separately and freeze the transport body once. Existing text-only HTTP/WebSocket routes reject image-bearing payloads.

The same request UUID and exact canonical text plus ordered descriptor manifest use one common manager acceptance/deduplication path. The bounded additive receipt `input:{text,attachments}` persists through lookup/restart. Repeating an accepted request returns its original identity even when staging/model selection later changes; different text, order or descriptor conflicts. Receipt metadata contains no image bytes, arbitrary filesystem paths or credentials.

Typed accepted events and engine visible/native history retain descriptors and internal image markers. Provider transports hydrate owned immutable artifacts immediately before serialization. Interrupted recovery reconstructs image-bearing input once and records uncertain tool evidence; it does not replay tools or inference merely because a receipt is restored.

## Frontend recovery boundary

The coherent frontend candidate scopes real Blob/raw-text/frozen-intent storage to account, full configured home URL, environment and session. Direct ready metadata without native Blob authority fails closed. Both actual composers pass the canonical selected provider/model; only an exact `imageInput === true` entry permits new image transport. Check is capability-free receipt/local-cleanup recovery. Explicit Retry GETs first, and only 404 permits current-model/pin revalidation followed by the unchanged frozen body. Scope and model ABA cannot adopt an old async result.

Writable legacy recovery admission can prepare the local imported head without image HTTP; read-only views cannot authorize that write. Choose original images stores transient ordered missing-pin choices. Save original images verifies and commits exact original bytes locally, preserving UUID/body/descriptors/IDs and newer draft; it does not upload, look up a receipt or send. The user then explicitly chooses Check or Retry. See [frontend integration](features/V4_USER_IMAGE_FRONTEND.md) and [native draft storage](features/V4_USER_IMAGE_DRAFT_STORE.md) for the source contracts.

## Private lifecycle

The private staging registry and bytes are separate from immutable tool/history artifacts. Session state fencing serializes acceptance, upload publication, cancellation, expiry collection and deletion. Files are privately created and opened without following symlinks. A shared session filesystem lease spans native turns and acceptance publication through history/snapshot commit; engine collection and retirement use an exclusive nonblocking lease. An active native writer makes engine collection skip while the actual staged read proceeds. Busy retirement returns a typed precommit failure before a tombstone or image deletion, and explicit deletion retry is required. Unconfirmed own process/resource cleanup and failures after deletion starts keep the session held. Before publishing bytes, a preparing reservation durably binds the upload UUID and complete descriptor. Only the same body can resume an incomplete reservation. A possible final ready commit keeps its bytes and identity even when durability acknowledgement fails. A lost response does not authorize rebinding an upload or send identity. Cancellation of an unknown canonical UUID reserves a bounded tombstone within the owned session, so a late initial upload cannot republish it.

Unaccepted staging expires after 72 hours. Tombstones prevent late republishing. Accepted/uncertain receipts pin image availability; compaction archives and independent forks retain their own immutable history copies. Idle collection considers accepted-event pins and complete owned native history/compaction archives before removing registry-known engine copies. Missing or unreadable history heads and archive/pin-read failures retain engine bytes and fail closed. Uncertain copies from a never-initialized engine head are retained until explicit scoped session retirement; absence of a head never proves that an existing image is unreferenced. Staging collection touches only typed images and exact generated crash-temporary basenames inside its private scope; unknown entries are retained and reported. It never sweeps arbitrary files or another scope. Retained history must survive ordinary draft removal/expiry, and original-session deletion must preserve independent forks.
